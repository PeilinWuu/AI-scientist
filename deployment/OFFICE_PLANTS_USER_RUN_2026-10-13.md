## 严重问题与原因

### P1：目标URL与来源编号冲突，执行器静默读取了另一个目标

两次真实动作记录均为：

```json
{
  "action": "read_source",
  "source_id": "S2",
  "url": "https://www.nature.com/articles/s41370-019-0175-9"
}
```

实际返回的URL却是：

`https://drexel.edu/engineering/news-events/news/archive/2019/November/potted-plants-dont-improve-air-quality/`

证据文件：项目目录下`artifacts/stage_action_intent_v5.json`和`stage_action_intent_v6.json`，以及`project.json`中的第5、6条background_agent.observations（从1计数）。

根因已通过代码确认：`src/ai_scientist/background_agent.py`的BackgroundAction共用schema同时接受source_id和url；read_source分支约566—590行只按source_id找来源，随后读取source['url']或缓存，不检查动作url是否与该来源冲突。模型虽然违反了「read_source使用已发现来源编号」的提示约定，但接口没有拒绝不一致参数，导致错误目标的读取以成功返回。已读页面中出现的论文链接也没有直接供read_source安全跟进并登记为新来源的路径。

这不是论文网站拒绝访问的问题：这两次根本没有向请求的论文URL读取。模型后续仍承认仅获取新闻稿，因此本次**没有证据表明最终报告已经伪造了原文阅读**，但工具执行契约和界面呈现已不可靠，足以阻止把本轮作为成功答辩示例。

### P1/P2：工具状态混合了意图、执行中和实际结果

`src/ai_scientist/research_timeline.py`约93—107行使用模型purpose作为工具折叠标题，仅根据completed等宽泛状态判断「工具已返回」。因此标题看起来像已读取Nature原文，展开后才发现实际是Drexel新闻稿。

`background_agent.py`约422—443行在执行前把动作暂记为interrupted；实时UI对它显示「行动未完成」。第二次搜索还在执行时即出现此文案，搜索真正返回后又变成「工具已返回」。用户无法区分进行中、确实失败和目标错配。

修复应分别呈现请求目标、实际目标、执行中/返回/失败状态。矛盾参数必须明确报错或要求模型重新选择，不得静默忽略。

## 其他观察

1. **等待不透明且耗时波动大。** 首个行动决策的提供商回执显示首片段137.261秒、首正文141.264秒、总143.716秒；下一次行动调用总8.989秒。不能把长等待都归因于Streamlit，也不能凭这一次确定是提供商排队、网络或模型内部处理。第二次搜索工具耗时81.96秒。需要区分模型等待和工具等待，展示真实动作及超时恢复，而不是统一「等待模型响应」。
2. **低信息检索结果。** 本轮两次检索产生10个URL候选，初始title/snippet空白。模型不得不额外打开网页才能知道来源身份；选源效率和判别能力受到影响。尚未诊断究竟是上游只返回链接还是项目解析丢失字段。
3. **重复读取没有视为无新增信息。** 两次相同新闻稿缓存读取耗时为0仍算completed，`consecutive_no_progress`随之归零。需要依据实际新增内容/读取范围识别无效循环，不能把重复I/O成功当研究进展。
4. **错误外链。** 公开回复中的裸URL紧接中文右括号和正文，前端生成的href把「）以获取具体CADR数值，并检索NASA」编码进URL。链接不可正确跳转。应保留原回复，同时规范引用渲染或提示模型使用规范Markdown链接。
5. **阅读负担仍大。** 开场连续展示问题形式化、研究模式和领域路由的大段文本，含Research Director、systematic_review、adopted_source_ids等实现术语。后续反复重述同一新闻稿结论，用户很难快速判断新增了什么。
6. **研究类型措辞过强。** 模型把4—6篇限定来源的任务直接称为「系统综述」，但尚未完成系统检索和筛选。应区分产品内部研究模式标签与实际达到的方法学标准。
7. **可恢复性有正面结果。** 真实Qwen调用、网页搜索和部分正文读取有效。HTTP403/超时没有伪装成成功；暂停保存有效。这些不等于全流程或科研结论通过。
